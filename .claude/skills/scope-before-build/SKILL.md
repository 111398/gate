# Scope before build

## Зачем это нужно

В проекте Gate теперь есть три специализированных субагента —
`.claude/agents/{backend,frontend,design}.md`. Чтобы правильно раздать им
задачи (и не переделывать работу из-за неверно понятого объёма), крупные
изменения нужно сначала описать письменным ТЗ и подтвердить с пользователем
— до того, как начнётся реализация. Мелкие правки в этом не нуждаются:
избыточное ТЗ на перекраску кнопки — это трение, а не польза.

## Когда срабатывает

Триггер — промпт подразумевает **хотя бы одно** из:
- **Новые компоненты** — UI-компонент, виджет, фича, новый экран/раздел.
- **Миграции** — любое изменение схемы Supabase (`supabase/migrations/`).
- **Сильное изменение дизайна** — редизайн раздела, изменение токенов
  (`_tokens.scss`), цветовой схемы, лэйаута.

НЕ срабатывает на: однострочные фиксы, орфографию/опечатки, перекраску
одной кнопки/элемента и подобные точечные косметические правки без
структурных изменений.

## Что делать

1. **Войди в режим планирования** (`EnterPlanMode`) — не начинай
   реализацию сразу.

2. **Задай уточняющие вопросы по промпту** (`AskUserQuestion`), пока не
   ясен объём. В зависимости от типа изменения уточняй:
   - *Новый компонент/фича*: где он должен жить (какой слой FSD —
     `entities`/`features`/`widgets`/`views`), с чем интегрируется
     (tRPC-роутер, existing UI из `shared/ui`), нужна ли отдельная
     локализация (ru/en), нужна ли поддержка обеих тем.
   - *Миграция*: что именно меняется в схеме, нужен ли RLS на новых
     таблицах, нужен ли Postgres-триггер для инварианта (см. паттерн в
     `CLAUDE.md` — "нельзя создать X без Y"), какая колонка/таблица
     — обратно совместимо или нет.
   - *Дизайн*: какой именно раздел/компонент, нужно ли заводить новые
     токены или использовать существующие, как это ложится на тёмную тему,
     не разъедутся ли отступы/разделители в соседних экранах
     (см. предупреждение про `SettingsSection` в `CLAUDE.md`).

3. **Составь ТЗ** внутри плана, со структурой:
   - Цель и контекст (что и зачем).
   - Затронутые области: backend / frontend / design — явно, кому из
     трёх субагентов какая часть.
   - Список файлов/директорий, которые будут созданы или изменены.
   - Зависимости между частями (например: миграция должна быть
     применена пользователем до того, как фронт начнёт использовать
     новую схему).
   - Критерии готовности: `pnpm lint && pnpm build`, для UI —
     обязательная живая проверка в браузере (десктоп/мобильная ширина,
     обе темы), для миграций — файл отправлен через `SendUserFile` и
     применение подтверждено пользователем.

4. **Получи подтверждение** через `ExitPlanMode`. Не начинай
   реализацию до явного "да" от пользователя.

5. **После подтверждения ТЗ маршрутизацию решай сам**, по факту
   содержания ТЗ: какие куски отдать `backend`-, `frontend`- или
   `design`-агенту, в каком порядке (учитывая зависимости из ТЗ — не
   параллель, если один блок реально ждёт другой), а какие — сделать
   самому напрямую, если после уточнений объём оказался меньше, чем
   казалось по первому промпту.
